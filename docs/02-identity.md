# 02 · Identity, enrolment, revocation

## One key per machine

A machine's identity is its WireGuard **node key**: a Curve25519 keypair generated by
tailcat on first run and never rotated. The public half is what peers pin and what the
passkey attests. There is no separate signing key: every message a machine sends to a
peer travels through a tunnel that already authenticates it, so nothing beam sends needs
a signature of its own. The only signature anywhere in beam is the passkey's, over an
attestation.

```
peerId = lowercase hex of the first 8 bytes of SHA-256(nodePublic)        16 characters
```

`nodePublic` is the raw 32-byte public key, not tailcat's `nodekey:` text form. The id
is derived, not minted, so every machine computes the same id for the same key. It is a
path segment (`mailbox/out/<peerId>/`) and is validated as exactly 16 lowercase hex
characters wherever it arrives from outside.

A `label` is a human name, defaulting to the hostname, local to each machine's view.
1–64 characters, no `/`, `\`, `{`, `}` or control characters. Rejected, never rewritten.

## `$BEAM_DIR`

`$BEAM_CONFIG_DIR`, else `$XDG_CONFIG_HOME/beam`, else `~/.config/beam`. Every file is
written as temp file → `0600` → rename over.

```
$BEAM_DIR/
  key.json           tailcat PrivateKey: node private key, disco key,
                     pre-shared key, DERP region                          0600
  fleet.json         { v, credentialId, passkeyPublicKey, attestation }   0600
  peers.json         PeerRecord[]                                         0600
  revocations.json   RevocationRecord[]                                   0600
  label              this machine's own label, one line
  mailbox/           see 05-mailbox.md
  run/beam.sock      control socket, present while the daemon runs        0600
  run/beam.lock      exclusive lock held by the running daemon
```

`key.json` is tailcat's own `PrivateKey` JSON (v0.7.0:
`{Private, Public:{ServerPublic, ServerDiscoPublic, PresharedKey, RegionID}}`), written
by tailcat's marshaller so the format tracks upstream. It is created by `beam init` or
`beam join` and never regenerated while it exists.

`fleet.json` exists only on a machine that has been attested. `passkeyPublicKey` is the
credential's COSE public key exactly as the authenticator returned it at registration,
base64url. `attestation` is this machine's own. **`init` and `join` are the file's only
writers.** Nothing refreshes it from anywhere.

## The attestation

An attestation is a WebAuthn assertion whose challenge is a hash over the machine's
transport identity. It states, under the owner's passkey: *this node key is one of mine.*

### Challenge

```
challenge = SHA-256( "beam-attest:v1" ‖ nodePublic ‖ discoPublic )        32 bytes
```

`"beam-attest:v1"` is 14 ASCII bytes and separates this from any other use of the
passkey. `nodePublic` and `discoPublic` are raw 32-byte keys. The disco key is included
because it is the second half of what peers reach this machine by; attesting it stops a
peer being steered to a different path-discovery identity than the one the owner
approved. The pre-shared key and DERP region are not attested: the PSK is a secret, the
region is routing.

### Record

```json
{
  "v": 1,
  "peerId": "…16 hex…",
  "nodePublic": "…base64url 32 bytes…",
  "discoPublic": "…base64url 32 bytes…",
  "credentialId": "…base64url…",
  "clientDataJSON": "…base64url…",
  "authenticatorData": "…base64url…",
  "signature": "…base64url…"
}
```

### Verification

Given an attestation and the verifier's `fleet.json`:

1. `peerId` is 16 lowercase hex and equals the derivation from `nodePublic`.
2. `credentialId` equals `fleet.credentialId`. A different passkey is a different owner
   or a lost passkey's predecessor: refuse.
3. Recompute the challenge from `nodePublic` and `discoPublic`.
4. Hand the assertion to `go-webauthn/webauthn` as a passkey login against a credential
   record built from `fleet.passkeyPublicKey`, with expected challenge from step 3,
   `RPID = "pair.n10.is"`, `RPOrigins = ["https://pair.n10.is"]`, user verification
   required, sign-count checking disabled (synced passkeys report 0, and an attestation
   is verified years later). The library checks `type == "webauthn.get"`, origin,
   `rpIdHash`, the UV flag and the signature over
   `authenticatorData ‖ SHA-256(clientDataJSON)`.

A failure at any step is a refusal with one of three reasons: `wrong-passkey`,
`bad-peer-id`, `bad-assertion`. No COSE is hand-rolled.

## The ceremony page

WebAuthn needs a browser on a real origin; a passkey is scoped to its relying party ID
and `localhost` is shared by every local program. So one static HTML file is hosted at
`https://pair.n10.is/`. It is the only thing beam hosts and it does exactly this:

1. Reads `location.hash`: `op` (`create` or `get`), `challenge` (base64url),
   `state` (opaque), `return` (a `http://127.0.0.1:<port>/cb` URL), and for `create` a
   `user` display name.
2. Calls `navigator.credentials.create(…)` or `.get(…)` with `rpId: "pair.n10.is"`,
   `userVerification: "required"`, and for `create`:
   `authenticatorSelection.residentKey: "required"` so a later `get` needs no allow list.
3. Navigates to `return#state=…&result=…` with the credential or assertion serialised as
   base64url JSON.

Everything after `#` never leaves the browser. The page makes **no network requests**
and this is enforced, not promised: it ships with
`Content-Security-Policy: default-src 'none'; script-src 'sha256-<hash>'` and an inline
script. It holds no state and verifies nothing. Anyone can view-source it.

The daemon side: open a one-shot listener on `127.0.0.1:<random port>`, generate
`state`, open the browser at the page URL with the fragment filled in, wait up to five
minutes for `GET /cb`, check `state`, hand the result to the verifier, respond with a
one-line "done, you can close this tab", close the listener. If no browser can be
opened (`beam init` on a headless machine, the rare first-machine case), the URL is
printed and the user forwards the port: `ssh -L <port>:127.0.0.1:<port> box`.

What a hostile page can do: pass a different challenge to the authenticator. The
daemon then rejects the assertion (challenge mismatch) and the tap was wasted. What
the attacker gains is an assertion over a challenge of their choosing, which is an
attestation for a key that no machine in the fleet has on any allowlist and no owner
will ever paste into `beam add`. This is the whole exposure and it is accepted.

## Enrolment flows

Three commands. `init` runs once per fleet, `join` and `add` once per added machine as
a pair. See [07-cli](07-cli.md) for the exact output.

### `beam init` — the first machine

1. Generate `key.json` (tailcat `PrivateKey`), pick the best DERP region.
2. Ceremony `create` with a fresh random challenge; store `credentialId` and
   `passkeyPublicKey`.
3. Ceremony `get` with this machine's attestation challenge; verify it against the key
   just stored; write `fleet.json`.
4. Start the daemon if it is not running.

Two taps. The second could be folded into the first by a page that does both, but two
distinct ceremonies keep the page trivial and keep registration and attestation
separately verifiable.

### `beam join` — on the machine being added

1. Generate `key.json` if absent.
2. Start a **join server**: a tailcat `Server` using this machine's real node key and
   disco key but a fresh random pre-shared key, allowing any client. Print its address
   (a `tc…` string of about 150 characters) and a QR code of it. This is the **join
   address**; it is different from the machine's permanent address and it is valid for
   ten minutes or one use.
3. Accept the first client that completes a WireGuard handshake. Record its node key.
   Stop accepting.
4. Over that tunnel, send `{ v, label, nodePublic, discoPublic, permanentAddress }` on a
   `sync` stream (see [04-streams](04-streams.md)) and wait.
5. Receive `{ passkeyPublicKey, credentialId, attestation, directory, revocations }`.
   Verify `attestation` is *this* machine's (its `nodePublic` matches) against the
   passkey key just received. Write `fleet.json`. Verify every attestation in
   `directory` against it; pin each one; write `peers.json` and `revocations.json`.
6. Tear down the join server. Start the permanent server with the allowlist set to
   every pinned peer. Start the daemon proper.

If step 5 fails verification, `join` exits non-zero, deletes nothing but `fleet.json`
(which was not yet written), and prints which check failed. The join address is
already spent.

### `beam add <join-address>` — on a machine that already has `fleet.json`

1. Parse the address. Dial it as a tailcat `Client` with the machine's own node key.
2. Open a `sync` stream; receive the newcomer's `{ label, nodePublic, discoPublic,
   permanentAddress }`. Confirm the tunnel's remote node key equals `nodePublic`.
3. Show the prompt:

   ```
   add "buildbox" (b7f3 9a21 0c4e 55d1) to your fleet? [y/N]
   ```

   The fingerprint is the newcomer's `peerId` grouped in fours. The newcomer printed the
   same id under its join address. Comparing is optional; the pasted address already
   authenticates the tunnel. The prompt exists so a paste into the wrong machine is
   noticed here rather than later.
4. Ceremony `get` with the newcomer's attestation challenge. Verify.
5. Send `{ passkeyPublicKey, credentialId, attestation, directory, revocations }` where
   `directory` is every pinned, unrevoked peer's `{ peerId, label, address, attestation }`
   including this machine's own.
6. Pin the newcomer. Add it to this machine's allowlist. Dial its permanent address to
   confirm; report `added "buildbox"`.
7. Gossip: on the next `sync` exchange with every other pinned peer, the newcomer's
   directory entry travels along (see "Gossip" below). Peers that are offline get it
   when they next connect to anyone who has it.

`add` refuses if `fleet.json` is absent (`run "beam init" first`) and if the newcomer's
`peerId` appears in `revocations.json` (`that machine was revoked; wipe its $BEAM_DIR to
give it a new identity`).

### Headless machines

`join` never touches WebAuthn, so a headless box needs no browser: `ssh box beam join`,
copy the address, `beam add <addr>` on the laptop. The owner's passkey is used on the
laptop. There is no device-code flow, no polling and no server.

## The peer table

```go
type PeerRecord struct {
    PeerID      string          // derived from NodePublic
    Label       string          // local display name, unique in this table
    NodePublic  []byte          // 32
    DiscoPublic []byte          // 32
    Address     string          // tailcat address: node, disco, PSK, region
    Attestation Attestation
    PinnedAt    int64           // unix ms
    LastSeenAt  *int64
    Revoked     bool
    RevokedAt   *int64
    Scopes      *[]StreamKind   // nil = all; see 04-streams.md
}
```

A record is created only by `join` or `add` (directly) or by gossip (after verifying the
attestation). There is no unverified or "directory-only" record: a machine either holds
a verified attestation for a peer or has no record of it.

**Label rule.** The far side's self-description is written when the record is created.
After that the local label is the owner's: renaming here never propagates, and a peer
changing its own label never overwrites what this machine shows. Collisions get `-2`,
`-3` suffixes.

**Default grant.** A new record has `Scopes == nil`, which means all three stream kinds.
One human, one fleet: every machine may open a shell on every other on first contact.
Narrowing is `beam peer grant <peer> msg` on the machine being protected.

## Sync and gossip

Every time a tunnel comes up between two pinned peers, each side opens one `sync`
stream and sends:

```json
{
  "v": 1,
  "label": "laptop",
  "directory": [ { "peerId", "label", "address", "attestation" }, … ],
  "revocations": [ { "revokedPeerId", "issuerPeerId", "issuedAt" }, … ]
}
```

The receiver, for each directory entry it does not hold: verify the attestation; if it
verifies, pin it (label from the entry) and add to the allowlist. For each it does hold:
update `address` if it differs (a machine that moved DERP region, or rotated its PSK).
Never remove. Revocations are applied as below.

This is the whole fleet directory. There is no server copy. A machine that has been
offline learns about newcomers from the first peer it reconnects to. With N machines,
every one hears about a newcomer within one round of reconnects.

## Revocation

```json
{ "v": 1, "revokedPeerId": "…", "issuerPeerId": "…", "issuedAt": 1758570000000 }
```

No signature. A revocation is accepted only when it arrives over a tunnel from a
**pinned, unrevoked** peer, or is issued locally. The tunnel is the authentication. When
B forwards A's revocation to C, C accepts it as *B's* revocation — anyone in the fleet may
revoke anyone, so the distinction has no effect.

**Effect** on receipt of an accepted record not already held: append to
`revocations.json`; if a peer record exists mark it revoked; remove the key from the
allowlist (see [03-transport](03-transport.md) for how, given tailcat's current API);
terminate every stream from that peer and the tunnel itself. Idempotent.

**Revocation is permanent for that `peerId`.** There is no un-revoke: every
`revocations.json` that holds it re-sends it in every `sync`, so a forgotten revocation
would return from the next peer. A revoked machine that should come back wipes
`$BEAM_DIR` (or `key.json`, `fleet.json`, `peers.json`, `revocations.json`), gets a new
node key and therefore a new `peerId`, and is added again. `add` enforces this.

`beam peer forget <peer>` is different: local amnesia, no record issued, nothing
propagates.

## Losing the passkey

The fleet keeps working: every pin is local and needs no passkey. What stops working is
adding machines, because no machine can produce an attestation under the old root and
no machine may accept a new root from a peer (that would let one stolen machine replace
the owner). Recovery is: `beam init --replace-root` on one machine (new passkey, new
`fleet.json`; peers and revocations kept), then `beam join` / `beam add` for every other
machine. Each keeps its node key and `peerId`; only `fleet.json` is rewritten. Pins
survive because a pin is a verified attestation plus a key, and the old attestation was
verified under the old root before it was rotated; a peer that joins under the new root
simply gets a new attestation.

## What is deliberately absent

- A device key separate from the node key. See "One key per machine".
- A hosted fleet list. Gossip.
- A device-code flow. `add` runs on the machine with the browser.
- Certificate expiry, key rotation schedules, sign-count tracking.
- Any way to add a machine without a passkey tap.
