# beam design critique — 2026-09-22

Reviewed `README.md`, then `docs/01-model.md` through `docs/11-decisions.md`, in that order, at commit `06c2ac6`. This is a prototype review: no recommendation is constrained by compatibility. **Blocker** means the specified mechanism cannot deliver its promised behavior; **critical** means fleet authority or isolation can be lost; **high** means material security, availability or durability failure; **medium/low** denote narrower defects or unnecessary complexity. Findings are ordered by severity within each section. References name the original specification's lines, not this review's.

Network verification used tailcat **v0.7.0**, commit `15ab9e68bfc6534a61797d7af28cedd42b54a3a5`, and its pinned Tailscale dependency `a2263542f260`, plus primary WebAuthn/browser/authenticator documentation. Source inspection is not a passing integration test. The local Go is 1.20.3; tailcat requires 1.27.1, so I did not compile it or reproduce its topology here. I did not perform real authenticator or browser ceremonies. Specific unresolved compatibility claims are identified below.

## 1. Trust model and cryptography

1. **Critical — One legitimate ceremony on a compromised machine permanently exports the fleet's membership authority.** Concern: `docs/01-model.md`, Principles and threat model, lines 28–30, 58–59, 105–106; `docs/02-identity.md`, Fleet keys and Ceremonies, lines 31–42, 149–152; D4/D5. **Attacker:** malware controlling the daemon user or daemon process. **Precondition:** the owner performs init, join or revoke there once. **Gain:** copy `S` or `MSK`, then mint unlimited members and revocations forever without the authenticator, including after that machine is revoked. Zeroing `MSK` cannot erase the attacker's copy; leaving `S` alive also lets honest code reconstruct it. Go/JavaScript allocation, crash dumps, swap and browser history make “never touches disk” an aspiration, not a property. HKDF-to-Ed25519 is a reasonable primitive composition; exporting a reusable root contradicts the stated security guarantee. **Recommendation:** use direct WebAuthn assertions whose challenge binds the exact canonical operation, fleet and key; retain the credential public key and verify RP ID hash, origin, challenge, signature and UV. This still permits transaction substitution by a hostile page/endpoint during approval, but does not hand it unlimited future signing power. Alternatively explicitly accept permanent root compromise from any ceremony endpoint and remove D5's stronger promise. Moving derivation into the page only reduces the trusted computing base if the browser is isolated from the compromised daemon; on the same compromised user account that isolation is not guaranteed.

2. **Critical — The worker serving the ceremony page can turn one tap into permanent root theft, so it is in the trust path.** Concern: `docs/01-model.md`, “No server in the trust path,” actor table and “The one trusted moment,” lines 35–37, 73–94; `docs/09-build-and-distribution.md`, The worker, lines 82–84, 126–139. **Attacker:** compromised deployment credentials, origin infrastructure, malicious page code or a privileged browser extension. **Precondition:** one ceremony loads attacker-controlled code. **Gain:** retain `S`, derive every future membership signature and read the directory; the exposure's *opportunity* lasts seconds, its consequences do not. The same worker serves ciphertext and executable code, so its worst case is not denial of service. CSP delivered by that worker can be replaced with the page. Even an unchanged `default-src` policy is not a blanket navigation prohibition, nor does it validate the fragment's `return` URL. CI hashes are not an independent browser trust anchor. This is materially stronger exposure than ordinary WebAuthn authentication, where the RP receives signatures rather than a reusable authenticator-derived signing secret. **Recommendation:** prefer direct assertions as above, validate operation and return destination, and state the origin compromise assumption honestly. Do not add a browser extension merely to preserve a false “untrusted server” claim; a separately trusted client/code-distribution model is an architectural choice, not a CSP tweak.

3. **Blocker — A fixed HMAC verifier cannot verify arbitrary request HMACs under the unavailable key.** Concern: `docs/09-build-and-distribution.md`, Authentication, lines 105–114; `docs/11-decisions.md`, D22, line 31. The worker has `V = HMAC(K_auth, "beam:verify")`, while a request carries `HMAC(K_auth, request)`. There is no comparison or derivation from `V` that validates the latter. The first request does not even transmit `V`, and the schema has nowhere to store it. **Attacker:** none needed to break the protocol; a shortcut that accepts the first unverified append additionally lets an observer of `fleetId` preclaim its namespace. **Precondition:** implementing the stated API. **Gain:** honest requests cannot be authenticated, or an improvised bootstrap becomes unauthenticated. **Recommendation:** use one conventional scheme: a random bearer capability over TLS with a stored hash is sufficient for the explicitly shared-access directory, with defined enrollment/namespace ownership; or store the actual HMAC key; or use a public-key request signature if proving fleet namespace ownership matters. A derived key used for both request signing and server verification is just another shared secret, not the claimed verifier construction. Define first creation, query-string coverage, canonical bytes, atomic allocation and idempotency. A ±5-minute timestamp window alone does not prevent replayed appends.

4. **High — Revocation does not reach healthy peers on existing tunnels.** Concern: `docs/02-identity.md`, Revoke and Sync, lines 185–190, 216–219; `docs/04-streams.md`, Sync, lines 103–112; `docs/06-control-socket.md`, Ceremonies, lines 103–111. **Attacker:** revoked machine B. **Precondition:** A revokes B after A–C have finished their one establishment-time sync, and C remains running. **Gain:** B retains shell access to C indefinitely; neither C's live tunnel nor its daemon start triggers another directory read. “Gossip on the next sync” does not schedule that sync. A queued worker append is likewise retried only after restart. **Recommendation:** propagate each newly learned member/revocation immediately on existing peer connections, with bounded retries and durable pending state, using the same sync protocol. Commit revocations before enabling application streams after reconnect, and serialize admission/open decisions against revocation application. Test revoke while all healthy tunnels remain up, not only revoke followed by reconnect.

5. **High — Even with working gossip, revocation is eventual and the directory can conceal it from fresh or isolated machines.** Concern: `docs/01-model.md`, Threat model, lines 102–108; `docs/02-identity.md`, Directory, lines 119–128; D7/D8/D9. **Attacker:** hostile directory, potentially cooperating with revoked B. **Precondition:** fresh C receives an old member entry but not B's revocation, or an existing C is partitioned from informed honest peers. **Gain:** B authenticates and receives the default shell grant before C learns the tombstone. Union semantics prevent deletion of *locally observed* revocations; they do not prove completeness or freshness of a first fetch. Worker-assigned sequence numbers and AEAD authenticate neither the log's latest head nor omissions. **Recommendation:** explicitly promise refusal only after a machine has durably learned a revocation. For stronger enrollment guarantees require an authenticated current checkpoint from a trusted online source before shells are enabled, accepting the availability cost. There is no immediate fleet-wide revocation guarantee while allowing offline operation with no freshness authority. Keeping eventual revocation is an acceptable trade; claiming otherwise is wrong.

6. **High — Default shell access makes a stolen member a fleet-wide credential compromise, not an isolated node compromise.** Concern: `docs/01-model.md`, actor table, lines 71–75; `docs/02-identity.md`, Default grant, lines 210–212; `docs/04-streams.md`, Scopes and environment, lines 125–146. **Attacker:** thief controlling any enrolled default-grant node. **Precondition:** it reaches other members before they learn its revocation. **Gain:** execute as each daemon's user, read their `key.json`, `fleet.json` and mailbox, modify local trust state, install persistence, and impersonate unrevoked nodes. File mode `0600` does not protect a file from that same user. It can also access the local control socket through remote exec; “local client only” is not a separate privilege boundary here. **Recommendation:** say that a shell-capable peer is transitively trusted as the owner's OS account across the reachable fleet, and that revoking one key does not evict an established attacker. For the personal prototype, accepting this is coherent; “nothing else is affected” is not. Do not market per-stream grants as a sandbox against an already shell-capable member.

7. **High — A revoked member can permanently exhaust directory capacity using credentials revocation never withdraws.** Concern: `docs/02-identity.md`, Fleet keys and Directory, lines 32, 40–42, 123–124; `docs/09-build-and-distribution.md`, caps and Authentication, lines 100–114. **Attacker:** current or revoked member holding `K_auth` and `K_dir`. **Precondition:** directory authentication has been made functional. **Gain:** consume all 2,000 append slots, or monopolize the shared 60-request/minute budget; valid new joins and revocations cannot append. At 60 appends/minute an empty log fills in roughly 34 minutes. Dropping bad signatures on read does not reclaim append capacity. Replays count too unless explicitly deduplicated. Revocation also does not stop this attacker decrypting future entries; it knows future machine addresses, not merely historical labels. **Recommendation:** acknowledge permanent directory read access as a deliberate non-goal unless keys rotate. Protect write capacity with server-verifiable authorization and bounded/idempotent storage, or choose a simpler directory representation that an authorized writer can repair. If encrypted opaque append-only records are retained, reserve/recover capacity through an owner-authorized mechanism and account for malicious writers explicitly. “Finer auth would protect nothing” is false: it protects availability.

8. **High — The allow-any exposure starts below beam's five-second timer and is not bounded by the per-key limit.** Concern: `docs/01-model.md`, Threat model, lines 109–111; `docs/03-transport.md`, Addresses and Admission, lines 34–57. **Attacker:** address holder, especially a revoked node, creating arbitrary fresh node keys. **Precondition:** ability to reach the relay/server and send tailcat discovery/admission traffic. **Gain:** consume transport peer state, handshakes, netstack resources and beam parser work. One simultaneous connection *per source key* imposes no global bound. Source inspection finds `onMeow` inserts unknown keys into a persistent clients map before beam sees TCP and rebuilds the network map; closing a beam connection does not remove that transport entry. **Recommendation:** measure and bound total unauthenticated transport state and global admission work, plus byte/deadline limits before allocations. This may require upstream support; do not silently fork around it. Application admission is a defensible personal-fleet trade, but only with an explicit denial-of-service acceptance, not a claim that a five-second socket timer bounds it. See the feasibility section for the absent removal API.

9. **High — An envelope's `from` field is not authenticated merely because its containing stream is.** Concern: `docs/02-identity.md`, One key per machine and Gossip, lines 5–8, 214–219; `docs/05-mailbox.md`, Envelope and Sequence numbers, lines 12–22, 46–51. **Attacker:** an admitted message-capable peer. **Precondition:** receiver trusts the envelope's `from`, `to` or sequence namespace rather than binding them to transport identity. **Gain:** impersonate another sender to subscribers and advance its high-water mark, suppressing future messages. The spec never requires those equality checks. **Recommendation:** require `from == authenticated remote peerId`, `to == local peerId`, safe integer/range validation and per-authenticated-sender storage; reject mismatches before deduplication. No machine signature is needed for direct envelopes with this binding. For gossip, the *root* signatures already authenticate forwarded member/revoke objects; the tunnel identifies the forwarder, not the original author. Verify every forwarded object independently, preserve revocations monotonically, and never gossip local grants or aliases as authority. Omitting an extra machine signature is an acceptable simplification, not itself a cryptographic flaw.

10. **High — Bidirectional message streams have no coherent grant check or single owner.** Concern: `docs/04-streams.md`, Msg and Scopes, lines 94–99, 116–127. **Attacker:** peer B whose incoming grant on A is `[]` or excludes `msg`. **Precondition:** A opens its own automatic `msg` stream to B; either side may send on it. **Gain:** B sends envelopes back through an A-opened stream without passing the check that guards B's opens. Also both daemons open one bidirectional stream, allowing two independent flushers to race a supposedly sequential queue. **Recommendation:** make `msg` directional, or explicitly check receiver-side grants per envelope and elect exactly one stream/one flusher per pair. Scope reduction must specify whether established message streams stop; per-open checks alone cannot implement that policy.

11. **High — A ceremony can disclose the root to a caller-supplied loopback destination without binding the displayed action to the actual operation.** Concern: `docs/02-identity.md`, Ceremonies, lines 135–154. **Attacker:** malicious local program or actor who persuades the owner to open a crafted genuine-origin ceremony URL. **Precondition:** a tap on a page displaying attacker-chosen label/action while returning secrets to an attacker-controlled local listener. **Gain:** reusable `S` and directory keys, without needing to alter `pair.n10.is`. A random `state` prevents unsolicited callback injection into an honest daemon, not an attacker initiating its own ceremony. **Recommendation:** return a signature bound to the full operation rather than the reusable seed; validate exact loopback host/path/port syntax, render untrusted strings as text and verify selected credential/derived root against the existing fleet on revoke. Same-user malware remains trusted under the current design, but the page must not present a descriptive sentence as cryptographic transaction binding. Define callback cancellation, malformed-state handling and concurrent tab behavior.

12. **Medium — Passkey loss is an accepted loss of administration, but the proposed recovery is not a defined or safe state transition.** Concern: `docs/02-identity.md`, Losing the passkey, lines 221–229; `docs/07-cli.md`, Enrolment, lines 41–42. **Attacker:** holder of a stolen node after the owner loses the passkey; otherwise no attacker is needed. **Precondition:** no usable synced credential remains. **Gain:** existing stolen credentials cannot be revoked under the old root. The prescribed `init` refuses existing enrollment, and manually deleting `fleet.json` leaves old peers, revocations, pending writes, mailbox counters and live sessions unspecified. **Recommendation:** accept new-fleet recovery for this prototype, but provide one daemon-owned reset/re-enroll operation, closing old connections and partitioning or clearing all root-dependent state atomically. Keep node identity only under an explicit rule; it is not a reason to preserve old trust. Explain that loss of the RP domain/usable browser path also disables administration even with the physical authenticator available. Synced passkeys reduce loss risk but move trust to provider/account recovery; they are not uniformly hardware-bound.

13. **Medium — Cryptographic encodings are too underspecified to be a protocol.** Concern: `docs/02-identity.md`, Fleet keys, Membership entry and Directory, lines 29–35, 83–98, 106, 116. **Attacker:** malformed-record producer or compromised member; interoperability failure needs no attacker. **Precondition:** different implementations interpret HKDF or canonical JSON differently. **Gain:** rejection of valid entries, ambiguous signed objects, or denial of service; this is not evidence of an Ed25519 break. **Recommendation:** specify HKDF hash, salt, info encoding and output lengths; use a defined canonical encoding with duplicate-key rejection, numeric ranges, Unicode/escaping and unknown-field rules. Verify `v` and `kind`, full key/signature lengths, and a nonzero PSK before admission; a parseable legacy/no-PSK tailcat address does not satisfy beam's advertised PSK policy. Specify random 24-byte nonces, the exact AAD bytes and version framing. Publish vectors. The two domain-separated PRF inputs are cryptographically reasonable; they do not require two ceremonies.

## 2. Feasibility against the real libraries

1. **Blocker — Independent tailcat stacks cannot reliably share the single node key in the proposed two-tunnel topology.** Concern: `docs/03-transport.md`, Two roles per machine, lines 14–25; D19. Each `Client` creates its own backend, engine, magicsock and WireGuard state using `Client.Key`; `Server` creates another. With A's server and A→B/A→C clients connected to the same DERP, all register the same destination key A. The pinned DERP server routes that key to one active connection; its default duplicate policy follows the most recent writer. Traffic intended for A's server can arrive at A→B's client stack, which admits only B and uses B's PSK, or vice versa. DERP has no beam-role/tunnel identifier with which to select the right stack. Distinct local UDP sockets do not repair relay routing. **Recommendation:** block implementation on a three-node, forced-relay topology spike and an upstream-supported architecture. Prefer one networking stack per node with bidirectional dialing support upstream, or consciously redesign transport identity and stream multiplexing. Separate client keys require a different signed identity binding; a shared reverse application session needs a mux if it must open arbitrary reverse streams. Neither is the specified design. Do not hide an unsupported stack-sharing patch inside `transport`. This is a source-derived failure argument, not a locally executed test. Evidence: [tailcat client initialization](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat.go#L1883-L1995), [pinned DERP destination lookup](https://github.com/tailscale/tailscale/blob/a2263542f260/derp/derpserver/derpserver.go#L1327-L1362), [duplicate writer selection](https://github.com/tailscale/tailscale/blob/a2263542f260/derp/derpserver/derpserver.go#L1700-L1724).

2. **Blocker — The browser callback never delivers the fragment containing the PRF outputs to the daemon.** Concern: `docs/02-identity.md`, Ceremonies, lines 143–152; `docs/06-control-socket.md`, Ceremonies, lines 93–94. Navigation to `/cb#state=…&result=…` requests `/cb` without the fragment. The daemon cannot check state or derive keys from that HTTP request; no callback page/script that reads the fragment and POSTs it is specified. **Recommendation:** define a small loopback landing page that reads, clears and submits the fragment through a same-origin POST, keeps the listener alive until submission, sends `no-store`, and suppresses secret logging. Prefer returning a bounded assertion instead of PRF seeds. Test a real browser navigation; the software authenticator directly calling the listener cannot catch this omission. Fragment behavior is defined by [RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986#section-3.5).

3. **High — tailcat v0.7.0 cannot individually terminate an inbound peer's WireGuard tunnel through its public API.** Concern: `docs/03-transport.md`, Admission, lines 55–61; `docs/02-identity.md`, Revoke, line 189. The source has `AddAllowedClient`, `Client.Close` and whole-`Server.Close`; it has no `RemoveAllowedClient`, per-peer disconnect or exported `PeerKey` method. Closing A's outbound client and every accepted beam TCP connection for B can stop beam operations, but B's inbound transport identity remains configured. Restarting the server affects every peer and, in allow-any mode, still admits B to transport. **Recommendation:** promise application-level denial and cancellation of all tracked streams/processes, and explicitly retain the transport DoS limitation. If removing inbound transport state is a requirement, request a supported upstream API before building. In particular, “add it to the allow set” must mean beam's own table: calling tailcat `AddAllowedClient` once switches the server out of allow-any and breaks unknown-member admission. Evidence: [allowlist API and lifecycle](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat.go#L862-L992), [transport peer insertion](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat.go#L1666-L1730).

4. **High — `Status` and WireGuard keepalives do not supply the specified dead-peer/reset oracle.** Concern: `docs/03-transport.md`, Connection lifecycle, lines 79–95. `Server.Status()` populates server-side peer/path observations; it is not status for all separate outbound `Client` stacks. A silent network partition produces retransmission/timeouts, not an immediate remote TCP reset. The spec supplies neither a dial deadline nor a liveness deadline, and its “one relay round trip” cost is not a timeout model. **Recommendation:** define `connected` as a recent successful authenticated exchange, measure liveness on the actual application connection, and specify deadlines, jitter and offline transitions. Report direction-specific or explicitly approximate path data. Do not show a server-side path as proof that the outbound stream works. Evidence: [Status implementation](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat.go#L1732-L1741), [Client.Ping timeout comment and Dial](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat.go#L2180-L2210).

5. **High — PRF compatibility is a browser × OS × credential-provider × transport matrix, not the product-name list in the specification.** Concern: `docs/02-identity.md`, Fleet keys and Ceremonies, lines 44–46, 153–154; `docs/11-decisions.md`, Q4, lines 56–59. **Recommendation:** replace blanket support promises with tested tuples and runtime checks of actual outputs. The verified evidence is:

6. **High — The described WebAuthn call and support detector are incomplete, although the create-then-get fallback is valid.** Concern: `docs/02-identity.md`, Fleet keys and Ceremonies, lines 23–27, 44–46, 140–142, 166–168; `docs/10-testing.md`, Software authenticator, lines 43–48. `create` needs `publicKey.rp`, user, challenge and algorithm parameters; `rpId` is a get option, and creation's UV requirement belongs in `authenticatorSelection`. Checking only that `.prf` exists accepts `{enabled:false}`. Registration can enable PRF without returning results; use `get` for that *same newly created credential*. Inputs must be bytes. **Recommendation:** specify actual request objects, preserve credential identity, inspect `enabled` at create and both 32-byte results at use, and distinguish canceled/unsupported/failed ceremonies. Browser capability checks cannot guarantee the selected authenticator supports PRF before creation. Keep `userVerification: required`; PRF itself is not a universal synonym for UV. The current standard's generic PRF is UV-state-independent; its CTAP `hmac-secret` mapping selects the UV PRF. It also hashes the caller's input with the WebAuthn PRF domain separator before authenticator evaluation, so the fixture's raw `HMAC(secret, salt)` is not “exactly” WebAuthn. Treat it as a test PRF, with separate real-browser coverage. Evidence: [WebAuthn PRF processing](https://www.w3.org/TR/webauthn-3/#prf-extension), [creation options](https://www.w3.org/TR/webauthn-3/#dictionary-makecredentialoptions).

7. **Medium — The verified tailcat API is usable, but several address/key assumptions are stale.** Concern: `docs/02-identity.md`, `$BEAM_DIR`, lines 55–65; `docs/03-transport.md`, Addresses and TCP, lines 29–32, 67–70. **Recommendation:** use upstream structs and helpers rather than reconstructing internals. 8. **Medium — A signed immutable relay address cannot survive arbitrary relay migration without a defined update rule.** Concern: `docs/02-identity.md`, Membership entry, lines 83–87; `docs/03-transport.md`, DERP, lines 99–105. A custom map flag does not rewrite signed entries already pinned elsewhere. Embedded relay coordinates may become obsolete, and different valid entries for the same node have no supersession rule. **Recommendation:** specify one authenticated address-update rule before advertising relay migration, or constrain the prototype to stable relay coordinates and explain the required re-enrollment/tap. This is a real use for `--derp-map`, not a gratuitous fallback, given the upstream public fleet's lack of permanence. Distinguish changing map fetch location from changing the signed rendezvous information.

9. **Medium — Test infrastructure claims are partly confirmed, but fake end-to-end tests omit the most fragile boundary.** Concern: `docs/10-testing.md`, Dev DERP, Software authenticator and Manual QA, lines 30–48, 94–105. `runDevDERP`, STUN and ConPTY do exist upstream. However upstream tests use both `IN_TS_TEST` and a captive-portal hook; the environment variable alone does not substantiate the claim that all external probes are disabled. No fake tests prove browser callback, PRF portability or QR behavior. **Recommendation:** retain deterministic protocol fixtures, add actual browser callback coverage, and make the supported real-device matrix an explicit gate before asserting one-tap enrollment. Use the upstream harness or precisely reproduce its network isolation, not just its environment variable. Sources: [tailcat TestMain](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat_test.go#L46-L70), [dev DERP](https://github.com/tailscale/tailcat/blob/v0.7.0/cmd/tailcat/tailcat.go#L1697-L1755), [Windows ConPTY implementation](https://github.com/tailscale/tailcat/blob/v0.7.0/tailcat_ssh_windows.go#L170-L210). The footprint numbers were not independently benchmarked; one-tunnel RSS is not evidence for an N-client-stack fleet.

## 3. Simplicity

1. **High — The filesystem mailbox recreates a transactional store without specifying its transactions.** Concern: `docs/05-mailbox.md`, Storage, Sequence numbers and Acknowledgements, lines 29–69, 100–106. Separate envelope, counter and high-water files plus link/rename/quarantine are multiple persistence mechanisms for one durable queue. Advancing `seen` before durable insertion can make a retry falsely ack a lost message; inserting first without recovery rules can redeliver it. Link/rename atomicity alone is not power-loss durability, and deleting outbound data after an ack only works if that ack follows a durable receiver commit. The explicitly allowed missing-counter restart at 1 silently discards new mail until it exceeds the old high-water mark. **Recommendation:** prefer one transactional local database for envelopes, counters and deduplication, or specify and test an equally rigorous filesystem commit/recovery protocol including file/directory sync. Fail closed on a missing counter for an existing identity; do not “fix” it by starting at 1. This is justified simplification for a product whose central promise is durability, not a request for another interchangeable storage adapter.

2. **High — Two directional tunnels plus bidirectional `msg` and `sync` duplicate ownership and obscure correctness.** Concern: `docs/03-transport.md`, Two roles, lines 23–25; `docs/04-streams.md`, Msg and Sync, lines 94–112. With both ends opening each bidirectional kind, a pair can have two long-lived message channels and redundant full-state sync exchanges. “Strictly sequential per peer” is not guaranteed by TCP when there are two TCP connections. **Recommendation:** first resolve the tailcat identity blocker; then choose one owner for each logical queue and one clearly directional or elected connection for each exchange. Preserve one application protocol rather than compensating with lock registries and reconcilers layered around duplicate flows.

3. **Medium — Local `forget` is a second, misleading removal mechanism that immediately fights automatic admission and gossip.** Concern: `docs/02-identity.md`, Revoke, line 192; `docs/06-control-socket.md`, Peers, line 84; `docs/07-cli.md`, command list, line 17. A forgotten valid member is rediscovered, and recreating its peer record risks restoring `Scopes == nil` after the user had restricted it. Forgetting a revoked record must not remove its permanent tombstone. **Recommendation:** delete `peer forget` from the prototype. Use revoke for trust removal and, only if actually needed, a view-only hide control that cannot affect policy. Do not introduce a new “forgotten but remembered” trust state to rescue a low-value command.

4. **Medium — Separate `pty` and `exec` grants advertise a privilege distinction the specification itself says does not exist.** Concern: `docs/04-streams.md`, Scopes, lines 118–131; `docs/07-cli.md`, `peer grant`, lines 18, 88. Both execute arbitrary code as the same user; either can create a shell or implement the other. The configurable combinations add UI and test cases without separating authority. **Recommendation:** keep both stream kinds for their useful I/O semantics, but expose only meaningful capabilities, such as command execution and messaging, if restricted nodes remain in scope. For an all-trusted personal fleet, deleting grants entirely is also coherent. Do not add `join --grant` as a second local policy mechanism with unspecified remote effect.

5. **Medium — Detached-daemon supervision has two policies and no single owner for deliberate shutdown.** Concern: `docs/06-control-socket.md`, Connect-or-spawn/Shutdown, lines 18–28; `docs/08-desktop.md`, Process model, lines 9–15. Every client spawns on missing socket, while desktop runs another timed restart policy. An explicit shutdown can look like a crash to another connected desktop and be undone. Five-second startup also includes potentially slow transport initialization unless control readiness is decoupled. **Recommendation:** define one daemon connection/spawn helper and distinguish deliberate stop from unexpected disconnect. Keep the control socket responsive while enrollment/network setup is pending. Delete the deferred `--install` promise from the current command contract until a service-managed lifecycle is chosen.

6. **Low — Several abstractions and historical explanations describe machinery the prototype does not need.** Concern: `docs/09-build-and-distribution.md`, Layout, lines 10, 16, 30–32; `docs/01-model.md`, lines 92–94; D15; `docs/10-testing.md`, lines 10–12, 78–79. Both `identity` and `ceremony` claim key derivation; blanket package import restrictions conflict with HTTP loopback ceremony and DERP-map work. No specified feature needs pluggable transport/storage providers: tailcat is the sole transport and the worker is the sole directory, while fakeworker is a test fixture. Previous-design comparisons, one-test-file-per-source-file and mandatory break-every-assertion ritual add instructions without defining behavior. **Recommendation:** give key derivation to `identity`, keep ceremony orchestration thin, permit necessary networking at the appropriate boundaries, and delete historical/process clutter. Keep narrow n10 integration seams and test fakes where they isolate real boundaries; do not turn them into production plugin frameworks.

7. **Low — The development flags describe two incompatible ways to share a relay.** Concern: `docs/10-testing.md`, Dev DERP, lines 36–39, 90; fake worker, lines 52–55. `--dev-derp` both starts a new relay and supposedly points multiple daemons at the same existing one. Config directory/endpoints are said to come from flags, while only some flags are named. **Recommendation:** let the test harness own one relay and worker and supply their endpoints through one documented test configuration. Keep the software authenticator release-excluded. `--derp-map` and `--json` have actual consumers and should stay; speculative Homebrew/installer details can wait.

## 4. Internal consistency

The following includes contradictory contracts and missing cross-document mappings, not merely spelling differences. Where a defect is explained above, the recommendation here identifies the specific reconciliation needed.

1. **Blocker — Unknown-peer admission waits for a frame the generic protocol forbids sending yet.** `docs/03-transport.md`, Admission, lines 52–54 and `docs/04-streams.md`, Admission/Sync, lines 11–12, 103–110 require the first sync frame to authorize an unknown opener; `docs/04-streams.md`, Frames, line 41 says frames begin only after the response. An opener waiting for `ok` and a receiver waiting for `self` deadlock. **Recommendation:** put `self` in the sync open header, or explicitly define a pre-admission sync flight and when success/refusal is returned. The opening claim at `04:4` that authentication finishes before any byte is read must distinguish tunnel identity from fleet authorization.

2. **High — The largest legal directory cannot fit the one-frame full-state sync.** `docs/09-build-and-distribution.md`, Storage, lines 94, 100 permits 2,000 entries up to 4,096 bytes; `docs/04-streams.md`, Frames/Sync, lines 46, 103–112 requires all records in one frame ≤1 MiB. Up to roughly 8 MiB of log entries is allowed, and gossip has no independent record-count bound. **Recommendation:** stream bounded batches through the existing framing, with revocations applied first, or reduce the stored-state bound to a demonstrably fitting amount. Do not silently truncate tombstones.

3. **High — Mail flush triggers omit the ordinary case of sending while already connected.** `docs/05-mailbox.md`, opening, lines 7–8 says only the `connected` transition triggers flush; Delivery, lines 73–76 adds startup and unacked retries; `docs/06-control-socket.md`, `msg.send`, line 117 promises a delivered outcome. No event wakes an idle flusher on a new outbound enqueue. **Recommendation:** specify one persistent per-peer flusher awakened by enqueue, reconnect and retry, and delete the contradictory opening restriction.

4. **High — Revoke and init success/failure have incompatible meanings after a worker outage.** `docs/06-control-socket.md`, Ceremonies, lines 99, 103 says wait completes once appended, while lines 106–111 says waits fail with `directory-unavailable` after local mutation and queued append; `docs/02-identity.md`, flows, lines 163, 178, 189–190 specifies no pending outcome; `docs/07-cli.md`, revoke result, lines 58–59 reports unqualified success. **Recommendation:** return a structured local-applied/directory-pending result, preserve idempotency and retry in-process. State precisely whether a canceled/timed-out ceremony may already have committed an operation.

5. **High — “Never consulted at runtime” contradicts the startup, revoke and recovery protocol.** `README.md:48–51`; `docs/01-model.md`, Principles, lines 35–40; `docs/02-identity.md`, Directory/Absent, lines 126–128, 236; versus `docs/06-control-socket.md:110–111` and D7 (`docs/11-decisions.md:16`). **Recommendation:** use the accurate contract everywhere: no polling; best-effort startup read; explicit enrollment/revocation writes; established streams continue during directory outage. State whether startup blocks on a fetch and for how long.

6. **High — Recovery commands contradict the enrolled-state guard and key-generation flow.** `docs/02-identity.md`, Init and Losing the passkey, lines 160, 224–227 says generate a key but later preserve node key/peerId; `docs/07-cli.md:41–42` requires manually deleting fleet state; `docs/06-control-socket.md:154–155` and D15 prohibit client file manipulation. **Recommendation:** define a daemon-owned fleet reset/re-enrollment transition and specify whether node identity is retained, including revocations, queues and pending directory entries. Do not ask a user to delete a live daemon's files.

7. **High — The “wrong root” test cannot reach another fleet's records through the specified directory addressing.** `docs/10-testing.md`, Integration tests, line 74 expects different PRF secrets to yield `wrong-fleet` after failing entry verification; `docs/02-identity.md:35, 173–175` derives a different `fleetId`, so the client normally reads a different namespace or gets a directory auth/not-found failure. AEAD under the wrong directory key fails before signature verification if foreign ciphertext is injected. **Recommendation:** separate wrong-credential selection, decrypt failure and invalid-membership-signature tests, and define empty/missing fleet behavior; do not let “join” create a fresh isolated fleet accidentally.

8. **High — The actor/decision claims disagree about where secrets exist and what is hardware-bound.** `docs/11-decisions.md`, D4, line 13 says the derived root can sign/encrypt without any of it on disk and calls it hardware-bound; `docs/02-identity.md:32, 56` explicitly caches directory/auth keys; `docs/01-model.md:51–52` permits synced credentials; `docs/01-model.md:58` says the private half exists only in daemon memory while `01:80–83` makes the page equally capable of deriving it. **Recommendation:** distinguish credential private key, exported PRF seed, derived membership key and cached directory capabilities; scope hardware claims to the authenticator type actually selected.

9. **Medium — The startup sequence starts a daemon that must already be running to perform it.** `docs/02-identity.md`, Init/Join, lines 164, 179; `docs/07-cli.md:56` says start after enrollment; `docs/06-control-socket.md:18–21, 92–104` and `docs/07-cli.md:3–5` require the daemon before enrollment. **Recommendation:** define an unenrolled daemon state with a live local control socket, then start the network service on successful enrollment. Use `not-enrolled` consistently for unavailable remote operations.

10. **Medium — The public directory schema cannot store its authentication or retention metadata.** `docs/09-build-and-distribution.md`, Layout/Storage, lines 24, 88–101 defines one entries table with only append creation time; Authentication, line 110 requires a per-fleet verifier, and line 101 expires by last request, including reads. **Recommendation:** define the minimal fleet metadata and atomic sequence allocation, or simplify the auth/retention design so the advertised schema is actually sufficient.

11. **Medium — Subscriber refusal and fan-out semantics do not support the desktop's state model.** `docs/05-mailbox.md:118–119` and `docs/06-control-socket.md:119, 122–123` provide one outstanding envelope until ack, with no reject/defer operation; `docs/08-desktop.md:35, 59–63` requires an `inboundRefused` view and leaves missing targets unacked. One missing pane blocks the desktop's whole subscription indefinitely, and beam has no information distinguishing “refused” from merely unacked. Multiple overlapping subscribers also have no ownership/ack rule for a shared envelope. **Recommendation:** choose competing-consumer semantics for the prototype, define ownership and reassignment, and delete the refused state unless the application stores/displays it itself. Define an explicit defer mechanism only if skipping blocked messages is required.

12. **Medium — Control replies can legally exceed their own line-size cap.** `docs/06-control-socket.md:35–36, 120` returns all queue entries on one line, while `docs/05-mailbox.md:40–42` permits 10,000 envelopes/64 MiB per peer per direction. `status`/`peers` have no fleet-size or result-size limit either. **Recommendation:** return bounded summaries and paginate queue listings with the same stable schema; keep payload retrieval separate if needed.

13. **Medium — The peer view cannot populate the desktop interface.** `docs/06-control-socket.md`, `PeerView`, lines 74–76 lacks `pinnedAt` and `inboundRefused`, which `docs/08-desktop.md:31, 35` requires; `inboundWaiting` has no type on the socket but is an item array in `08:34`. **Recommendation:** define one wire peer view, use counts/summaries there, and remove unsupported desktop fields rather than inventing client disk reads.

14. **Medium — Prefix peer arguments have no corresponding control-socket contract.** `docs/07-cli.md`, Peer arguments, lines 121–122 accepts unique ≥8-hex prefixes; `docs/06-control-socket.md:87–88` accepts only full IDs or labels. **Recommendation:** perform all resolution in the daemon, documenting precedence when a label looks like a hex prefix, and return the same candidates for CLI and desktop.

15. **Medium — Labels are both rejected without rewriting and returned after unexplained collision suffixing.** `docs/02-identity.md:18–19`; `docs/06-control-socket.md`, `peer.rename`, line 83; label ambiguity at `06:87–88` and `07:121–122`. **Recommendation:** allow duplicate display labels and require ID disambiguation; delete automatic suffixing. If suffixing is selected instead, specify its algorithm, persistence and length behavior consistently.

16. **Medium — Version negotiation is attributed to headers that do not exist on the control socket.** `docs/09-build-and-distribution.md`, Versioning, lines 62–64 says the socket carries `v:1` in every open header; `docs/06-control-socket.md:39–43, 56, 129–130` has no such field. `v:1` belongs to the peer stream header at `docs/04-streams.md:19–23`. **Recommendation:** keep transport and control versions distinct and define one control handshake/version field; do not infer control compatibility from an application semver caret range.

17. **Medium — Scope and revocation language promises states the admission rules cannot deliver.** `docs/04-streams.md:122` says `[]` opens no stream, but lines 125–127 exempt sync; line 127 says sync teaches a peer it was revoked, while `docs/03-transport.md:51` closes revoked peers without reading. **Recommendation:** say `[]` denies application streams, and revocation is enforced by informed receivers without depending on notifying or persuading the revoked machine. Do not conflate grant reduction with revocation.

18. **Medium — Stable error vocabularies are incomplete and unmapped across boundaries.** Identity verification uses `revoked` at `docs/02-identity.md:98`; mailbox/control use `revoked-peer` at `docs/05-mailbox.md:86` and `docs/06-control-socket.md:146`. `invalid-topic` and `payload-too-large` appear as send outcome reasons at `05:86–87`, but no complete wire-ack reason set exists despite `04:97` and test claims at `docs/10-testing.md:11–12`; `seen-unreadable` first appears at `05:104–105`. Distinguish malformed signature from an actually selected wrong fleet where possible.

19. **Medium — The single-daemon lock has incompatible exit codes.** `docs/06-control-socket.md:13–20` first says a second daemon fails, then says a racing spawn loser exits 0; `docs/07-cli.md:63–65` and `docs/10-testing.md:76` require exit 1. **Recommendation:** make daemon lock conflict consistently nonzero, and have connect-or-spawn reconnect to the winner instead of treating that child exit as final failure.

21. **Medium — Socket override and directory naming do not compose in remote scripts.** `docs/04-streams.md:139–145` injects `BEAM_DIR` and `BEAM_SOCKET`; `docs/08-desktop.md:79–81` expects CLI discovery through `BEAM_SOCKET`; `docs/02-identity.md:50` reads `BEAM_CONFIG_DIR`, while `docs/06-control-socket.md:9–11` never specifies an override. **Recommendation:** define socket-override precedence in the shared client connector and either standardize one directory environment name or expressly identify `BEAM_DIR` as informational. Otherwise an explicit `BEAM_SOCKET` can be ignored and a second config directory spawned.

22. **Medium — The npm shim contract omits the behavior needed for interactive shells.** `docs/09-build-and-distribution.md`, npm packages, line 73 says `execFileSync` with same argv and propagated exit code; `docs/07-cli.md:92–98` requires terminal ownership, resize, streaming stdio and signals. Node's synchronous child invocation needs explicit inherited stdio and careful nonzero-exit/signal handling, not just its default captured buffers. **Recommendation:** specify the thin launcher's terminal/signal behavior and verify `npx beam connect`, piped exec, Ctrl-C and resize, not only direct binary execution. This is a missing contract, not evidence that Node cannot launch the binary. [Node child-process documentation](https://nodejs.org/api/child_process.html#child_processexecfilesyncfile-args-options).

24. **Low — The declared filesystem is missing persistent files required elsewhere.** `docs/02-identity.md:53–62` omits `derpmap.json` from `docs/03-transport.md:101` and `pending/` from `docs/06-control-socket.md:110`. Its “every file temp → chmod → rename” at `02:50–51` also conflicts with mailbox exclusive linking at `docs/05-mailbox.md:40–41` and is inapplicable to live lock/socket paths. **Recommendation:** make the tree complete and scope write guarantees to each data class.

25. **Low — Exit-code and size claims use inconsistent or unspecified units.** `docs/07-cli.md:6–7` reserves remote exit status only for exec, while `07:92–94` gives it to connect too. `docs/02-identity.md:18` and `docs/05-mailbox.md:110` count characters without defining Unicode units, while headers, frames and payloads count bytes (`docs/04-streams.md:16, 46`; `05:25`). ## 5. The open questions

Recommendations are ordered by risk, with the original question number preserved. Each answers the question in `docs/11-decisions.md` rather than treating it as implementation permission.

1. **Critical — Q1's Ed25519 convenience costs the non-exportable authority that D5 claims to preserve.** Concern: Q1, lines 37–44. **Recommendation: use direct WebAuthn assertions for membership and revocation.** A reviewed verifier is preferable to exporting a permanent fleet signing seed into every joining machine. Bind the assertion challenge to a canonical operation and validate the selected root, RP/origin and UV; define how fresh machines obtain and authenticate the root's credential public key. Page-side Ed25519 signing is a smaller exposure only under a separately defended browser, and still exports authority to page code. If simplicity wins over this property, keep PRF-derived Ed25519 but rewrite the threat model as an explicit decision that all ceremony endpoints are trusted for the lifetime of the fleet.

2. **Critical — Q3's “same residual as every passkey RP” premise understates what the page can steal.** Concern: Q3, lines 50–55. **Recommendation: reject the equivalence and do not build the extension/hash-checking layer.** Direct assertions reduce compromise to approvals while the attacker controls the ceremony, rather than reusable future signing authority. A malicious page can still substitute an operation during a tap, so independently meaningful operation display remains necessary if transaction intent is a goal. CI pinning helps release integrity, not an origin the attacker can redeploy. A mandatory browser extension would create another distribution and trust system larger than this prototype's ceremony; either accept the origin as trusted or choose a separately authenticated/native approval surface deliberately.

3. **High — Q2 treats transport denial of service as bounded without a bound.** Concern: Q2, lines 45–49. **Recommendation: retain application admission only conditionally, after the topology and resource-budget spikes pass.** Unknown signed entrants do need an admission route, but the choice is not solely allow-any versus permanent worker push: manually importing a signed entry or reaching an existing member during enrollment are simpler alternatives if the exposure proves unacceptable. They sacrifice the one-tap/no-introducer UX. For the intended UX, the acceptable trade is bounded application admission plus explicitly accepted residual transport DoS, with any required peer-state limits provided upstream. Do not silently turn on `AddAllowedClient` after first admission.

4. **High — Q6 conflates a completed local revocation with failed dissemination.** Concern: Q6, lines 63–66. **Recommendation: apply locally, durably queue dissemination, and report partial propagation explicitly.** Failing the entire operation because the directory is down would leave the initiating machine exposed even though it can safely refuse the key immediately. Retrying must not require another tap. Immediately gossip to connected peers, retry the directory in the running daemon and expose pending status. Return success for durable local application with a clear pending-distribution field/message, while never claiming that disconnected uninformed peers are protected.

5. **High — Q4 cannot promise selected-authenticator PRF support before creating a credential.** Concern: Q4, lines 56–59. **Recommendation: preflight browser capability where available, then inspect actual creation output and handle unsupported credentials honestly.** The authenticator may ignore the extension, and successful creation may return enabled-without-results. Do not initialize a fleet until the required derivation/assertion checks succeed; offer an explicit “use another passkey provider/security key” retry, explaining that an unused credential may already have been created. That constraint is acceptable for an initial prototype with a published tested matrix. Remove the stale blanket Firefox exclusion and distinguish missing support from QR portability failures.

6. **High — Q7's proposed join flag cannot enforce restrictions on other machines under the present model.** Concern: Q7, lines 67–68. **Recommendation: keep all-access enrollment only if every machine is trusted as the owner's account; do not add `join --grant msg` as described.** Grants currently belong to each receiving machine, so a joiner choosing its own local grant cannot make the fleet treat it as report-only. Meaningful fleet-wide restriction would require a root-signed capability in the membership entry and a deny-by-default admission rule honoring it on every receiver, including future ones. Decide whether that capability is required now; if not, omit the flag and clearly label local grants as local policy. The default shell grant has the lateral-compromise consequence discussed above.

7. **Medium — Q12's inactivity timeout silently removes the only cold-start discovery source.** Concern: Q12, lines 77–78. **Recommendation: no inactivity deletion for the prototype; keep explicit bounded capacity instead.** Existing members retaining entries does not help a new machine that has neither their addresses nor an introducer path. Under a no-poll design, a healthy fleet can have no directory requests for years; the two-year threshold measures directory use, not fleet abandonment. If service economics later require expiry, implement an explicit authenticated repair/republish or introducer path and visible retention policy first. Changing the number does not fix the disconnected recovery story.

8. **Medium — Q8 evaluates preimage resistance but ignores that the short ID is a storage and revocation key.** Concern: Q8, lines 69–71. **Recommendation: use at least 128 bits for stored identity, retaining short prefixes for display.** A targeted 64-bit second preimage remains much harder than a chosen-pair birthday collision, and signed membership constrains practical exploitation; this is not an immediate unsigned attacker admission bypass. Nevertheless queues, tombstones and lookup tables key by the short value, so full-key admission checking alone does not prove collisions harmless. With no compatibility to preserve, 16 extra hex characters are cheaper than proving every map handles collisions safely. Always detect conflicting full keys and fail closed rather than overwriting a record.

9. **Medium — Q5's give-up state would strand the very offline messages beam promises to deliver.** Concern: Q5, lines 60–62. **Recommendation: retain automatic retry, use jitter and a longer capped backoff when idle, and reset promptly on user demand or network change.** Going permanently dormant until user action is another presence state that callers must understand and can prevent unattended delivery forever. A small fleet does not justify a hosted presence service. Measure the actual cost of tailcat's independent engines, relay registrations and timeout behavior first; the document's one-round-trip estimate is not a battery measurement. Bound each dial so backoff actually advances.

10. **Medium — Q9 proposes Windows support without tests for the platform-specific behaviors it exposes.** Concern: Q9, line 72. **Recommendation: defer Windows release until named-pipe, process lifecycle and ConPTY tests run on Windows CI.** Cross-compilation proves none of pipe ACLs, resize, signal/exit mapping, hard-link storage behavior or descendant cleanup. Copyable upstream ConPTY code is useful evidence of feasibility, not a tested beam implementation. A Unix-first prototype deletes platform branches and shrinks the initial verification surface; if Windows is necessary for the owner's fleet, adding its runner belongs in the first implementation slice rather than a later promise.

11. **Medium — Q10's timeout starts after the remote process can already have side effects.** Concern: Q10, line 73; `docs/06-control-socket.md:50–62, 129–130`. **Recommendation: attach before spawning the remote process, or make opening on the attach connection itself the single stream-creation transaction.** Ten seconds is a reasonable abandoned-reservation cleanup default, not a reason to execute a command before its consumer is ready. A loaded Electron process should get a retryable expired reservation, not a killed command it cannot tell executed. Increasing the timer or adding a user flag treats the symptom. Specify bounded output buffering and cleanup on local attach EOF/reset as well as explicit close.

12. **Low — Q11 would spend root ceremonies on cosmetic mutable data.** Concern: Q11, lines 74–76. **Recommendation: keep the enrollment label immutable in the certificate and local aliases local; no fleet-wide rename operation yet.** Identity is the full key, not the label, and a local alias already solves the stated interface need. If a real fleet-wide naming requirement appears, first define how multiple signed entries for one key supersede one another; `issuedAt` alone has clock/tie/replay problems. Do not add a generic metadata versioning system solely to make a personal machine label mutable everywhere.

13. **High — The decision list omits who attests freshness and what revocation completion means.** Concern: D7–D9 and Q6 (`docs/11-decisions.md:16–18, 63–66`). **Recommendation:** add the question “Can a fresh or partitioned node grant shells without evidence that it has current revocations?” Answer yes only with explicit eventual-revocation semantics; otherwise name the checkpoint/online authority and availability cost. Also decide whether “complete” means local, directory-persisted or observed by every reachable peer, and expose that distinction without pretending an offline peer acknowledged anything.

14. **High — The decision list omits crash consistency, sender reset and subscriber ownership for durable mail.** Concern: D11/D14 and mailbox specification. **Recommendation:** add one durability decision specifying the ack transaction, power-loss guarantee, replay semantics, counter-loss behavior and competing-consumer ownership. Require failure-injection tests around persistence boundaries. “Durable” needs a precise loss/duplication contract before choosing files versus a database; subscriber action and ack cannot provide exactly-once external effects without application cooperation.

15. **High — The decision list omits approval binding, credential selection and root replacement.** Concern: D4/D5/D20. **Recommendation:** decide whether a tap proves only possession of an owner credential or approval of the exact machine/revoke operation, how a second credential at the same RP is detected, and what state changes atomically during reset. Add a wrong-passkey test at revoke so an unrelated root cannot locally mark a peer revoked while producing a tombstone everyone else rejects. The present “one passkey” policy does not prevent the browser from offering old or unrelated credentials.

16. **Medium — The decision list omits resource and stream ownership limits below the visible per-peer caps.** Concern: D6/D10/D19 and `docs/03-transport.md` Admission. **Recommendation:** explicitly decide the maximum retained unknown transport identities, total admissions, full sync size, pending ceremonies, retained mail and child cleanup behavior after network loss. Define one owner for reconnects and each queue. These are required bounds for the chosen model, not opportunities for a configuration flag per limit.

17. **Medium — The decision list omits the permanent rendezvous and recovery dependency on `pair.n10.is`.** Concern: D4/D7/D16/D20. **Recommendation:** distinguish operational stream independence from administrative dependence on RP-origin continuity, passkey-provider continuity and the ability to find a surviving peer after directory loss. Decide how a relay-address change is signed and selected. State domain loss and total directory loss as explicit recovery scenarios; open-sourcing the worker alone does not let a different domain answer for existing WebAuthn credentials.

## 6. UX

The requested walk-through has a happy path only after the blockers above are resolved. The findings below preserve the order of operations inside each scenario; scenarios are ranked by the risk of misleading the owner.

1. **High — Revoking machine two from machine one reports more protection than machine one can establish.** Concern: `docs/02-identity.md`, Revoke, lines 185–192; `docs/07-cli.md:58–59`; `docs/08-desktop.md:47–48`. A selects B, opens the browser, chooses a passkey and verifies. The page must distinguish “remove B” from its generic “Add buildbox” sentence and bind it to the intended root. A then drops its own B streams, but connected C does not receive a fresh sync, offline machines cannot learn anything, and an unavailable worker queues a write until restart. The CLI says other machines “will refuse it as they next connect,” concealing both delays and the possibility of B reaching an uninformed node first. **Recommendation:** show “Revoked on this machine,” then “Published to directory” / “Pending publication” and the number of peers that have acknowledged the tombstone, without waiting forever for offline nodes. Refresh dissemination while the daemon runs. Warn about fleet re-enrollment after actual endpoint compromise because shell access could have copied other node keys; this is a consequence of this specific trust model, not a generic security banner. Do not offer forget adjacent to revoke as if both remove access.

2. **High — Init on machine one can succeed cryptographically yet leave a fleet the UI cannot finish or retry.** Concern: `docs/02-identity.md`, Init, lines 158–168; `docs/06-control-socket.md`, Ceremonies; `docs/07-cli.md`, Enrolment; `docs/08-desktop.md:40–45`. The owner clicks Create a fleet or runs `beam init`. A client first spawns an unenrolled daemon, whose readiness is unspecified. Region discovery can wait before a ceremony URL appears. The browser may ask which provider, ask for a PIN/biometric, create a credential, then require a second assertion; “one tap” does not explain that second prompt. The fragment callback currently cannot finish at all. If directory append fails after `fleet.json` is saved, retrying init says already enrolled, leaving the user with an error after a real state change. **Recommendation:** show stages—starting daemon, preparing network, choose passkey, verify, saving fleet, publishing—and explain any second verification. Return a resumable publication-pending result and preserve the successful credential. Provide a way to cancel/retry without deleting files. Ask for a recognizable fleet/passkey display name so later browser credential selection is not a list of indistinguishable accounts.

3. **High — Join on machine two confuses possession of a passkey with having a usable browser-to-daemon return path.** Concern: `docs/02-identity.md`, Ceremonies/Join, lines 149–154, 170–183; `docs/07-cli.md:44–56`; `docs/08-desktop.md:40–45`. On a second laptop, Join opens a local browser, the user selects the existing credential or scans its WebAuthn QR with a nearby phone, and the daemon derives the fleet and downloads the log. That is a plausible flow for a tested PRF tuple. Opening the printed URL directly on a phone is different: `127.0.0.1` now means the phone, not machine two. On a headless rack machine the specified answer is an SSH `-L` command, which requires another working remote-access mechanism, a terminal and access to a local browser; QR hybrid only connects authenticator to browser, not browser to remote daemon. **Recommendation:** state a browser on the target machine or an existing forwarded loopback port as a prerequisite. If terminal-free headless enrollment is required, this design does not meet it; choose a supported native/device enrollment flow rather than presenting QR as that solution. Show exact forwarding instructions, callback reachability, selected fleet fingerprint, cancellation and directory-progress feedback. Return an explicit wrong/empty-fleet result before writing a new enrollment, and distinguish “membership saved” from “N peers reached.”

4. **High — A third machine joining while two is offline has no clear convergence or retained-revocation story in the UI.** Concern: `docs/02-identity.md`, Join/Sync; `docs/03-transport.md`, Lifecycle; `docs/08-desktop.md:43–45`; `docs/10-testing.md:65`. C obtains the directory, learns A and B, joins A and keeps retrying B. C should show A connected and B offline with a next retry, not an unexplained “joined; 3 machines known” as proof of connectivity. When B comes online, it must learn C through direct authenticated contact or an A sync; learning a new record must also schedule a client/dial and update the UI even if that record arrived by gossip rather than unknown-peer admission. If B was revoked in the preceding scenario, it must remain revoked and never be dialed by C; bringing it online must not resurrect it. **Recommendation:** test both the unrevoked-offline case and the revoked-offline case. Apply all fetched revocations before dialing, specify the pin→dial/event transition, and show pending reachability separately from membership. If the directory omits B's tombstone, disclose that the no-freshness design cannot promise safe cold-start admission. If the directory has expired or lost all entries, C has no way to find A despite A retaining the complete history; show failure rather than a successful isolated join.

5. **Medium — Opening a PTY from two to one leaves waiting, disconnect and cleanup behavior undefined.** Concern: `docs/07-cli.md`, Streams, lines 92–98; `docs/06-control-socket.md`, Attach and Streams, lines 50–62, 129–133; `docs/04-streams.md`, PTY, lines 63–78. B runs `beam connect A` or selects a remote terminal. If A is offline, the reader cannot tell whether this immediately returns `offline`, triggers an immediate dial or waits through the current 60-second backoff. Once the remote process starts, the local attach can time out before Electron is ready. Network failure can leave TCP waiting while the terminal stays raw; only an explicit opener close is stated to kill the process group. Remote exit, signal, transport failure and successful shell exit need distinguishable feedback. **Recommendation:** specify a short bounded connection attempt with a visible connecting state and cancellation, attach before spawning, restore terminal mode on every local exit path, and define child cleanup on abnormal EOF/reset. In desktop, show connection loss in the terminal pane rather than a spinner forever. State that tmux holds durable sessions, whereas beam's ordinary PTY child is tied to the stream. Define login-shell invocation and a safe default when `$SHELL` is missing or invalid; calling an executable named by `$SHELL` is not by itself login-shell mode.

6. **Medium — Message status and passkey recovery force users to infer state from misleading text or manual files.** Concern: `docs/05-mailbox.md`, Send outcomes, lines 82–95; `docs/07-cli.md:41–42, 105–114`; `docs/08-desktop.md`, Mail relay, lines 59–63. `queued` also covers an online receiver that did not ack, so “not connected right now” is false in some ordinary cases. Pane injection followed by a crash before ack can be repeated, while one missing pane blocks the desktop's subscription. Passkey-loss recovery currently demands file deletion outside the desktop's promised daemon API. **Recommendation:** report “Stored locally; delivery pending; do not resend,” adding the actual reason when known; distinguish recipient-daemon delivery from application consumption. Expose blocked inbound items and a defined retry/defer policy without implying exactly-once pane injection. Provide reset/re-enroll through the same CLI/socket/desktop flow with explicit effects on queues, so recovering the fleet does not require filesystem surgery in a terminal.
